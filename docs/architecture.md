# Архитектура Zapys

Состояние на 15 ноября 2026. Снято с живой системы: сайт этого репозитория и проект Supabase
`oleg-unified-brain` (`ykhvfjbolifnpstftpzk`, eu-central-1).

## Из чего собрано

```
Клиент / лид
    |
    +-- Telegram: @zapysua_demo_bot ------> zapys-bot ----+
    |                                                      |
    +-- Сайт zapys-ua.github.io                            |
          |  index.html      форма заявки --> zapys-lead --+--> PostgreSQL
          |  book/index.html страница записи -> zapys-api --+    (Supabase)
          |  partners/       партнёры --------> zapys-api --+
          |
          +-- t.me/avenue_studio_ua  (переписка, Олег вручную)
```

Платные компоненты: только Supabase и Telegram, оба на бесплатных тарифах. Хостинг сайта —
GitHub Pages, домен `zapys-ua.github.io` бесплатный. Платного домена сознательно нет.

## Слои

**Сайт.** Три статические страницы без сборки и зависимостей: главная, страница записи,
партнёрская программа. Логика на инлайновом JavaScript. Публикуется GitHub Pages из `main`.
Файлы и каталоги, начинающиеся с точки, в публикацию не попадают, поэтому `.claude/` остаётся
служебным.

**Функции.** Supabase Edge Functions, Deno и TypeScript.

| Функция | Версия | JWT | Назначение |
|---|---|---|---|
| `zapys-bot` | 4 | нет | Обработчик webhook Telegram: диалог записи, напоминания, отзывы; с 18.11 привязка веб-брони по ссылке `?start=r_<код>` |
| `zapys-lead` | 2 | нет | Приём заявок с формы на главной |
| `zapys-api` | 4 | нет | API страницы записи, сертификатов и партнёрской страницы; с 18.11 бренд, модули, пакет сферы, продажа сертификатов |

`verify_jwt` выключен у всех трёх: иначе Telegram и статические страницы не смогли бы их вызывать.
Значит проверка входа лежит на самой функции, и это та граница, где нужен
**principle-boundary-discipline**.

Рядом в том же проекте живёт инфраструктура Avenue Studio: `memory-api`,
`revenue-os-ceo-read`, `revenue-os-owner`. К Zapys они не относятся и в задачах Zapys не
затрагиваются.

**Данные.** PostgreSQL 17 с включённым RLS на всех таблицах.

| Таблица | Назначение |
|---|---|
| `zapys_businesses` | Бизнесы: услуги, цены, мастера, график |
| `zapys_bookings` | Брони |
| `zapys_sessions` | Состояние диалога с ботом |
| `zapys_leads` | Заявки с формы |
| `zapys_crm` | Лиды холодного канала и этапы воронки |
| `zapys_playbook` | Сценарии продаж |
| `zapys_certs` | Подарочные сертификаты |
| `zapys_waitlist` | Лист ожидания |
| `zapys_partners` | Партнёры |
| `zapys_packs` | Пакеты сфер: словарь, поля, циклы напоминаний, статусы, шаблоны (с 18.11) |
| `zapys_subjects` | Объекты обслуживания: клиент, авто, питомец; уникальный ключ в бизнесе (с 18.11) |

## Свойства, которые должны держаться

**Идемпотентность бота.** Telegram повторяет доставку webhook при таймауте или ошибке. Повторная
доставка не должна создавать вторую бронь, второй сертификат или второе напоминание.
См. **principle-make-operations-idempotent**.

**Невозможность двойной брони.** Обещание с сайта. Защита должна стоять на уровне данных, а не
только в интерфейсе: интерфейс можно обойти, открыв страницу записи и бота одновременно.

**Один график на три входа.** Бот, мини-приложение и страница записи пишут в одну таблицу броней.
Расхождение между входами — нарушение обещания.

**Открытые функции.** Три функции доступны без JWT из интернета. Каждая обязана проверять, что
пришло, и не принимать на веру содержимое запроса.

## Чего в архитектуре нет

Ни платёжного провайдера в коде (кнопка предоплаты ведёт наружу), ни CRM-интеграции, ни рассылок
через внешний сервис, ни CI. GitHub Actions не настроены сознательно: лимиты.
